## 6. Adversarial findings — anything that weakens, or admits weaker provenance than the GPT join (item 6)

### R1 (PRIMARY, REQUIRED) — the Claude form never cross-binds the independent artifact's *content* to the sealed review; a self-authored review can pass
The GPT form cross-binds an independent-origin artifact's *content* to the sealed review: the `~/.codex/sessions` rollout (written by the codex process, not the lead) must have its final message equal the event-stream final (:739) and must cite the sha256 of review.json/REVIEW.md/review-freeze.json (:741-743). A lead cannot fabricate this without actually running an independent gpt-6.1-sol review that emits those digests.
The Claude form does **not** do this. `task_bytes` is read and then discarded (`task_bytes, task_pin = pinned(task_output_path)`, :822 — `task_bytes` is never referenced again); `reviewer_agent_id` is checked only for non-emptiness and as a filename substring (:823-825); `raw-final-message.txt`'s sha256 is bound but its content is never compared to anything. Nothing forces the sealed review (freeze + review.json + REVIEW.md + checks.json + raw-final-message.txt) to have *originated from* the independent task-output transcript. Consequently a lead can run any trivial subagent (to produce a genuine `subagents/agent-<id>.jsonl`), self-write the entire sealed review, assert `different_from_author:true`, and adopt. Independence is reduced to a self-asserted boolean plus an inert byte-pin. §23.6 (:4388-4393) explicitly claims the join "refuses … author-reviewed" and reserves the "not a loosening" judgment to this review; on the anti-author-review axis the Claude form is **weaker** than the GPT join. This is the one place adoption could proceed on weaker provenance than the original GPT join demanded.
**Required change:** bind the sealed review to independently-originated bytes — e.g. require `raw-final-message.txt` (or the task-output's final agent_message) to cite the sha256 of REVIEW.md/review.json/checks.json (mirroring :741-743), and/or verify `raw-final-message.txt` equals the task-output's final message, so the task-output pin stops being inert. (Equivalently, §23.4 should be respecified to add this binding.)

### R2 (REQUIRED) — `completed_at` requirement is unsatisfiable by the real freeze format
As in §4: `claude_review_join` requires a non-empty `completed_at` (:815-817) but both real freezes have `completed_at: None`. Fail-closed, so not a loosening, but the Claude form cannot adopt any real review until the freeze-sealing format is changed.
**Required change:** §23.6 must either ratify adding a sealed `completed_at` to the Claude-review freeze format (a change to the sealing step, not just the join) bound to an independent completion-time source (consistent with R1), or specify an alternative sealed completion-time source.

### R3 (REQUIRED) — shared sidecar check is incompatible with the 3-file Claude roster
`review_profile_problems` unconditionally pins `bound-inputs.json` and `tool-topology.json` from the review dir for **both** forms (:876-878). `pin` raises `FileNotFoundError` on a missing file (:446-454). The Claude roster excludes those sidecars (:92; comment :8-10 "no bound-inputs/tool-topology sidecars") and the real v10/v11 freezes seal only 3 files. So for a Claude review without those two files, `review_profile_problems` raises and `adopt`/`frame_admitted` crash. Fail-closed (not a loosening), but it makes the Claude form non-adoptable unless the lead also fabricates the two GPT-era sidecars — contradicting the 3-file design.
**Required change:** make the sidecar check form-aware (skip `bound-inputs`/`tool-topology` for `reviewer_kind == 'claude-subagent'`) or reconcile `CLAUDE_REVIEW_ROSTER` with the profile check.

### Noted (disclosed, acceptable; not blocking)
- **mode representation.** Real freezes store `mode` as the string `"0600"`; `Dir.ident` returns `mode` as an int. `claude_review_join` deliberately compares only sha256+bytes (:809), not mode, which is *necessary* given the format (a comparison would always refuse). The files are read via `read_observed` (single-link regular, O_NOFOLLOW; :253-273), so mode is not a load-bearing binding here. Recommend §23.6 normalize the freeze `mode` to int so the Claude form can bind it as the GPT form does (:709).
- **`REVIEW` path constant** `FRAME/'review/gpt61-v1'` (:71) retains a GPT-specific basename; the join reads via `Dir.anchor(REVIEW)` and does not depend on the basename, so this is a cosmetic non-join follow-up (AUTHOR-NOTES §4), not a defect in the join.
